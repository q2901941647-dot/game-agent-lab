# Game Agent Lab

**游戏知识库问答 Agent 与效果评测平台** · 

一个**真实可运行、可复现**的 AI 应用与评测闭环。重点不在于「能不能答」，
而在于 **答案是否可靠、是否可追溯，以及每一轮优化到底带来了多少可测量的变化**。

锚点游戏：《崩坏：星穹铁道》　|　知识库快照 KB-HSR-v0.3　|　标准测试集 HSR-GoldenSet v1.2（24 题）

## 一、这个项目想解决什么问题

这个岗位需要的能力不是「会用 AI 工具」，而是：**维护知识库、评估模型输出、调整提示词、推动应用落地**。

这类能力很难用几张 AI 生成的漂亮图来证明。它的证据形态只能是——**一个真实运行的系统 + 一份可复核的评测记录**。

于是我把「玩家查一条游戏机制」这件小事做成了一条闭环：

```
知识库整理 → Prompt / 检索策略设计 → 标准测试集评测 → 错误归因 → 改知识库与提示词 → 复测对比
```

## 三、指标可以在命令行复算（重要）

页面上所有数字都能离线复算，用来证明它们不是「成品截图」：

```bash
node tools/selftest.js
```

真实输出：

```
指标               v1 初版     v2 优化          变化
准确性              70.8%    100.0%    +29.2 pt
完整性              63.2%     83.3%    +20.1 pt
依据可追溯             0.0%    100.0%   +100.0 pt
时效性              91.7%    100.0%     +8.3 pt
稳定性              95.8%     83.3%    -12.5 pt
综合得分             65.6%     94.2%    +28.6 pt

完整验收：v1 0/24 → v2 22/24
```

注意**稳定性那一行是下降的**：v2 引入拒答阈值后，处在阈值边缘的问题在换一种问法时可能从「作答」翻转为「拒答」。
提高准确性的代价是边界稳定性下降——这是这一轮迭代暴露出的真实权衡，也是下一步调参的依据，而不是一句「优化后全面提升」。

## 四、知识库设计

每条条目包含 `id / cat / title / keywords / content / points / source / srcType / version / date / status / topics`：

- **来源分级**：官方 / 攻略站 / 社区，用于冲突取舍
- **版本标记**：标注资料对应的游戏版本，是时效性评测的基础
- **状态字段**：有效 / 待复核 / 已过期

刻意保留三类**真实病灶**，用来验证评测体系抓不抓得住它们：

| 病灶 | 条目 | 用来检验 |
| --- | --- | --- |
| 资料冲突 | 社区称保底 80 抽 vs 官方公示 90 抽 | 能否做来源取舍并显式提示冲突 |
| 资料过期 | 3.0 版本的混沌回忆配队 | 能否识别版本时效，不把旧结论当现结论 |
| 范围边界 | 跨游戏问题、未来版本问题 | 能否在无依据时拒答，而不是硬答 |

## 五、两套提示词策略

| 配置 | v1 初版 | v2 优化 |
| --- | --- | --- |
| topK | 3 | 5 |
| 范围边界 / 冲突样本条目 | 不纳入 | 纳入 |
| 来源加权 | 关闭 | 官方权重 ×1.18 |
| 强制引用来源 | 否 | 是 |
| 拒答规则 | 无 | 覆盖率 < 0.20 或检索置信度 < 25（校准值）或命中边界条目 |
| 冲突 / 过期提示 | 无 | 有 |

两套提示词的**原文**可在 Demo 的「Agent 问答」页直接查看，改一个词就能看到输出变化。

## 六、评测口径

| 指标 | 口径 | 权重 |
| --- | --- | --- |
| 准确性 | 行为是否符合预期（该答的答、该拒的拒、该提示的提示） | 35% |
| 完整性 | 人工标注的评分要点被覆盖的比例（二元组重叠 ≥ 50% 记命中） | 20% |
| 依据可追溯 | 答案是否标注了可回溯的知识库来源 | 15% |
| 时效性 | 是否把过期资料当作有效结论直接使用 | 15% |
| 稳定性 | 换一种问法后，行为与首要依据是否一致 | 15% |

**两级判定**（为什么不能只报一个总分）：

- **内容通过** = 行为正确 且 要点覆盖 ≥ 50%
- **完整验收** = 内容通过 且 依据可追溯

v1 的内容通过率看着不差（16/24），但完整验收是 **0/24**——因为它的答案**没有任何来源标注、不会拒答、不会提示过期与冲突**。
「答得像」和「答案可靠」是两件事，这正是这个项目最想说明的。

## 八、界面与动效

视觉系统为**深空藏青 + 星轨青 + 鎏金**。动效原则是**只服务于信息层级**，不做装饰性噪音：

| 动效 | 位置 | 说明 |
| --- | --- | --- |
| 星轨画布 | hero | 220 个星点缓慢漂移 + 偶发彗尾，离开视口自动暂停 |
| 极光漂移 | hero | 18s 循环，仅改 `top`（关键帧占用了 transform） |
| 滚动视差 | hero | 星轨 / 极光 / 标题分层位移，标题随滚动渐隐 |
| 滑动指示器 | 顶部页签、v1·v2 分段控件 | 药丸滑到当前项 |
| 数字滚动 | 评测 KPI | 65.6% → 94.2% 用 easeOutCubic 滚出曲线 |
| 进度条生长 | 证据相关度、要点覆盖率 | 错峰生长，覆盖率条按档位换色 |
| 卡片错峰进场 | 全部卡片 | 逐张递增延迟 |
| 闭环点亮 | 总览「项目运行闭环」 | 01→04 编号依次点亮，把「循环」做成可见的 |

全部动效尊重 `prefers-reduced-motion: reduce`。

## 九、已知局限

1. 当前是**离线确定性引擎**：检索与作答逻辑真实运行，但未接入真实 LLM。
   接入后需要增加「同一问题多次采样」的稳定性评测。
2. 知识库是**个人快照**：覆盖核心机制、少量角色与当前版本活动，未覆盖全角色与剧情。
3. 评分依赖**关键词与要点覆盖**：语义等价但措辞差异大的回答可能被低估，后续可引入 LLM-as-judge 做二次校验。
4. v2 引入拒答阈值后**边界问题稳定性下降**（95.8% → 83.3%），阈值仍需按业务容忍度继续校准。
5. 24 题中有 2 道跨条目推理题**未修复，已明确列为已知局限**，而不是从测试集里删掉。
